# PHASE2_AMFID_VERIFICATION — независимая проверка IOS-SEC-003 (vm_read double-fetch)

Метод: полный разбор `sub_100004030` в `amfid_B3.bin` (все 4 `vm_read`),
границы функций, источники адреса/размера. `amfid_B2`/`B3` — инструкции
идентичны, поэтому вывод применим к обеим сборкам.

**Критерий double-fetch (по ТЗ):** нужно показать ДВА обращения к ОДНОМУ
изменяемому источнику с существенной проверкой/решением между ними. Одноразовый
copy-out недоверенной памяти — это защита, а не дефект.

---

## Что читается (факт)

В `sub_100004030` два разных буфера читаются через `vm_read` из адресного
пространства вызывающего:

1. **Profile body** (vm_read @0x100004260): источник — `x1=x20` (адрес) и
   `w2` от `x26 length` — то есть указатель+длина берутся из `NSData`
   (profile), переданного клиентом. Цель — локальный буфер `x3/x4`
   (out-params `[sp,#0x50]`).
2. **profileAuxSig** (vm_read @0x100004300): `x22 → profileAuxSig` (NSData),
   `[x19 bytes]`→`x21` (адрес), `[x19 length]`→`w2` (длина), цель — `x3=x20`
   (`[sp,#0x68]`), `x4=x27` (out).

## Число чтений (факт)

- По КАЖДОМУ полю — **один** `vm_read`. profile body читается 1 раз
  (@0x100004260), profileAuxSig — 1 раз (@0x100004300).
- Это ДВА РАЗНЫХ источника, а не один и тот же буфер дважды.
- `[NSData bytes]`/`length` вызываются по одному разу на поле — указатель
  и размер извлекаются один раз и передаются в один `vm_read`.

## Используется ли копия последовательно (факт/инференция)

- При `vm_read`-ошибке (`cbz w0 → loc_100004328/ac`) в out-параметры
  пишется 0 (`str xzr`/`str wzr`), логируется `unable to vm_read
  profileAuxSig`/`%s not valid`, и поле помечается invalid — то есть
  при неудаче использования сырого указателя НЕТ.
- Успешный путь кладёт скопированные данные в out-params (x20/x27) —
  то есть дальше работает с **локальной копией**, а не с указателем
  клиента. Это стандартный copy-out.

## Есть ли основания считать данные изменяемыми между check и use

- **Нет прямых оснований в разобранном коде.** Между чтением `bytes`/`length`
  и `vm_read` нет повторного обращения к тем же полям — адрес/длина
  вычисляются один раз и используются в одном вызове.
- Гипотеза double-fetch требовала бы ВТОРОГО `vm_read` по тому же
  `bytes`/`length` (или повторного `[NSData bytes]` с последующим чтением)
  ПОСЛЕ проверки подписи — его в функции нет: всего 4 vm_read, из них
  в `sub_100004030` — 2, на разных полях.

## Проверки в вызывающих функциях (факт)

- `AMFIService` mutating-методы (`commitProfileForUuid:`, `stageProfileForUuid:`)
  — все вызывают `verifyBoolEntitlement:` (см. PHASE2_IPC); вход защищён
  entitlement'ом. Функция `sub_100004030` вызывается из этой gated-цепочки.

## Вердикт IOS-SEC-003

**→ RULED OUT (не double-fetch).** Код делает одноразовый copy-out
недоверенной памяти через `vm_read` для каждого из двух независимых полей
(profile body, profileAuxSig), при ошибке обнуляет out и помечает invalid,
при успехе работает с локальной копией. Признаков «чтение→проверка→повторное
чтение того же изменяемого буфера» не обнаружено.

Остаточная оговорка (INSUFFICIENT→низкий приоритет): теоретический TOCTOU
между `[NSData bytes]`/`length` и `vm_read` существует у любого
vm_read-from-client (клиент может перераспределить буфер), но это
свойство API, а не конкретный дефект — и `vm_read` возвращает ошибку на
невалидном диапазоне, что код обрабатывает. Отдельной уязвимости здесь нет.
