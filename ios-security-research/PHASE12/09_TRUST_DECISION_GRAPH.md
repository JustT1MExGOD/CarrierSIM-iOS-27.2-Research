# Граф решения доверия с маркировкой доказательств

## 1. Граф

```text
[входной MIG-запрос]
        │
        ├─[ПРЯМО ПОДТВЕРЖДЕНО] проверки формата/границ
        │       └─ ошибка → [ответ с кодом формата]
        │
        └─[ПРЯМО ПОДТВЕРЖДЕНО] sub_10000b194
                │
                └─ вызов sub_100004030
                        │
                        ├─[ПРЯМО ПОДТВЕРЖДЕНО] обнуление выходов
                        ├─[ПРЯМО ПОДТВЕРЖДЕНО] AMFIPathValidator_ios allocation/init
                        ├─[ПРЯМО ПОДТВЕРЖДЕНО] validateWithError:
                        │       │
                        │       ├─[НЕДОСТУПНО] внутренний контракт метода
                        │       └─ успех → извлечение результатов
                        │
                        ├─[ПРЯМО ПОДТВЕРЖДЕНО] computedCdHash
                        ├─[ПРЯМО ПОДТВЕРЖДЕНО] signerType
                        ├─[ПРЯМО ПОДТВЕРЖДЕНО] isValid
                        ├─[ПРЯМО ПОДТВЕРЖДЕНО] areEntitlementsValidated
                        ├─ profileData
                        │       ├─[ПРЯМО ПОДТВЕРЖДЕНО] vm_read успех → profile-like flag=1
                        │       └─[ПРЯМО ПОДТВЕРЖДЕНО] vm_read отказ → очистка профиля,
                        │                                      переход к auxiliary
                        └─ profileAuxSig
                                ├─[ПРЯМО ПОДТВЕРЖДЕНО] отсутствует → продолжение
                                ├─[ПРЯМО ПОДТВЕРЖДЕНО] vm_read успех
                                └─[ПРЯМО ПОДТВЕРЖДЕНО] vm_read отказ → журнал + очистка

[упакованный MIG-ответ]
        │
        └─[НЕДОСТУПНО] реальный внешний клиент и его решение
                ├─[ГИПОТЕТИЧЕСКИ] isValid=1/profile_valid=0 принимается
                └─[ГИПОТЕТИЧЕСКИ] комбинация влияет на защищённую операцию
```

## 2. Два разных вопроса

Граф разделяет:

- **производство данных:** что пишет `amfid`;
- **решение политики:** что считает допустимым клиент.

Смешение этих уровней и создавало риск преждевременной квалификации P9-H1 как уязвимости.

## 3. Уровни доверия к рёбрам

- `CALL`: подтверждённый `bl`, `objc_msgSend` или видимая передача управления.
- `DEP`: зависимость по `LC_LOAD_DYLIB`, не вызов функции.
- `INFERRED`: согласованная интерпретация регистра/поля, не достаточная для окончательного вывода.
- `UNAVAILABLE`: требуемый бинарник, тело метода или клиент отсутствует.

## 4. Итог графа

На producer-стороне есть подтверждённый частично успешный путь получения данных. На границе policy decision отсутствует подтверждённое ребро от комбинации полей к разрешению действия. Поэтому финальная квалификация остаётся консервативной.
