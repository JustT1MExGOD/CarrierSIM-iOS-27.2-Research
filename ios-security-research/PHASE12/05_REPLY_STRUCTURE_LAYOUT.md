# Структура и раскладка MIG-ответа

## 1. Статически наблюдаемые смещения

Ниже приведены адреса, которые видны в `sub_10000b194`. Поле считается семантически названным только при наличии прямого доказательства; близость к вызову не является достаточной.

| Смещение в reply | Наблюдаемое содержимое | Статус имени |
|---:|---|---|
| `+0x18` | служебное/message-related значение | прямо видно, точный тип не установлен |
| `+0x20` | код ошибки на отклонённом входном сообщении | прямо поддерживается ветвью `0xfffffed0` |
| `+0x24` | байт из локального выхода `sub_100004030` | поле результата, точное имя не доказано |
| `+0x28` | 32-битное значение из локального выхода | возможно `signerType`, но не окончательно доказано |
| `+0x34` | второй байт из локального выхода | возможно профильный флаг, но имя не доказано |
| `+0x38` | второй 32-битный результат | точное имя не доказано |
| `+0x3c` | NDR-запись | служебное MIG-поле |
| `+0x5c` | длина/метаданные переменной части | подтверждено операциями длины |
| `+0x64` и далее | переменная строковая/данная область | подтверждено `strlen` и копированием |
| `+0xa4` | байт из локальной временной структуры | точный смысл не доказан |
| `+0xa8` | два 32-битных значения | служебная/переменная часть, точный смысл не доказан |

## 2. Связь с локальной структурой

После вызова `sub_100004030` используются пары значений, загруженные из областей стека `[sp,#0x64]` и `[sp,#0x5c]`. Эти значения записываются как байт и 32-битное слово в `reply`. Такая упаковка подтверждает передачу нескольких независимых величин, однако без определения исходной структуры и протокола нельзя надёжно сказать, какая пара соответствует `isValid`, `signerType`, `profile_valid` или другому полю.

## 3. Не следует путать

- байтовое поле MIG-ответа с общей ошибкой вызова;
- положительный флаг с разрешением операции клиентом;
- нулевую длину профиля с криптографическим отказом;
- продолжение функции с успешным итогом протокола.

## 4. Частично подтверждённая гипотеза отображения

Ранее предполагалось:

- `reply+0x24` — `isValid`;
- `reply+0x28` — `signerType`;
- `reply+0x34` — `profile_valid`;
- `reply+0x38` — дополнительный флаг/длина.

Эта схема согласуется с порядком копирования и Phase 9, но в текущей доказательной базе остаётся **косвенно поддерживаемой**, а не прямой. В итоговом выводе она не используется как установленный факт.

## 5. Почему это важно для P9-H1

Для подтверждения уязвимости нужны одновременно:

1. точное соответствие полей;
2. доказательство достижимости комбинации;
3. описание клиентской проверки;
4. последствие для защищаемой операции.

Один только факт записи двух байтов в `reply` эти условия не выполняет.
