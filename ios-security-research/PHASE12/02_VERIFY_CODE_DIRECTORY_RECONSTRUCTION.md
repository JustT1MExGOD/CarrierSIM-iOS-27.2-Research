# Восстановление `verify_code_directory` (`sub_100004030`)

## 1. Идентификация

Источник: `amfid_B3_disasm.txt`, диапазон дизассемблирования `0x100004030–0x1000043f4`.

Функция начинается с пролога ARM64e (`pacibsp`) и резервирует `0x120` байт стека. Её роль — подготовить и заполнить набор результатов проверки для вызывающего MIG-обработчика.

## 2. Наблюдаемый порядок операций

1. Сохраняются регистры и создаётся локальное пространство.
2. По адресам выходной структуры записываются нули: байтовые/32-битные флаги, указатели и длины.
3. Проверяется security-token-подобный вход. Ненулевой токен приводит к журналированию `bad security token` и завершению по ошибочному пути.
4. Из пути строятся `NSString` и `fileURLWithPath:`.
5. Выделяется `AMFIPathValidator_ios`.
6. Выполняется `initWithURL:withFileOffset:withFlags:`.
7. Через динамическую отправку вызывается `validateWithError:`.
8. При успешном результате читаются остальные свойства и выходные данные.

## 3. Первичная инициализация — прямое доказательство

Инструкции `0x100004068–0x10000409c` обнуляют несколько выходных адресов, включая указатели/длины и флаги. Поэтому любой результат, который не будет явно записан позднее, остаётся в безопасном с точки зрения отсутствия данных нулевом состоянии.

## 4. Результаты после `validateWithError:`

После успешного ненулевого результата в `x21` вызываются:

- `computedCdHash:withLength:`;
- `signerType`;
- `isValid`;
- `areEntitlementsValidated`;
- `profileData`;
- `profileAuxSig`.

`signerType`, `isValid` и `areEntitlementsValidated` записываются независимо отдельными инструкциями. Это доказывает независимые места записи, но не доказывает независимую политику клиента.

## 5. Исправленная ветка `profileData`

Наблюдаемый фрагмент:

```text
0x100004260: bl  j__vm_read
0x100004264: cbz w0, loc_1000042ac
0x100004268: ldr x8, [sp, #0x60]
0x10000426c: str wzr, [x8]
0x100004270: str wzr, [x19]
0x100004274: b   loc_1000042b8
```

При успехе в `0x1000042ac–0x1000042b4` записывается `1` в профильный флаг. При ошибке два профильных выходных значения обнуляются, после чего управление переходит в `0x1000042b8`, то есть в начало обработки `profileAuxSig`.

Это не переход к терминальному cleanup-блоку. Следовательно, прежняя формулировка о прямом выходе с общей ошибкой исправлена.

## 6. Ветка `profileAuxSig`

Если объект отсутствует, обработка продолжается к финальному пути. Если объект присутствует, его `bytes` и `length` передаются в `vm_read`. При ошибке код журналирует `unable to vm_read profileAuxSig: %d`, обнуляет два auxiliary-выхода и продолжает завершение.

## 7. Что не доказано

- Внутренний порядок проверок внутри `validateWithError:`.
- Условия, при которых метод возвращает успех при несовпадении профиля.
- Полная семантика каждого адреса выходной структуры.
- То, что нулевой профильный флаг интерпретируется клиентом как разрешение.

## 8. Вывод

`sub_100004030` — производитель составного результата и отдельный обработчик получения дополнительных данных. Он не выглядит местом, где после `vm_read` выполняется единое окончательное решение политики. Наблюдается частичное сохранение первичного результата при сбое получения `profileData`, но security-значение этого состояния требует анализа потребителя.
